00 — CONTEXTE BB

BUBBLE-BLUE — Contexte et Besoins

Qu'est-ce que BB ?
  • BB est un protocole de communication privée multihop utilisant uniquement Bluetooth (sans réseau cellulaire ni infrastructure Wi-Fi)
  • Permet à un petit groupe d'appareils d'échanger des messages chiffrés
  • Utilise des ensembles dominants connexes (CDS) pour une dissémination contrôlée
  • Comme Bluetooth n'offre pas de diffusion native, toutes les transmissions passent par des séquences d'unicasts
  • Référence : arXiv:2509.00967 — Achir, Jacquet (2025)
  • Double usage : militaire (liaisons tactiques chiffrées) et civil (messagerie mesh privée)

BB impose 7 contraintes architecturales indépendantes du transport radio. Chaque choix technologique de cette présentation est évalué contre ces 7 besoins.

ÉTAT DE L'ART — BITCHAT (2/2)

BitChat — Déduplication, Relay Logic et Store-and-Forward

Les mécanismes anti-boucle et de persistance — leçons pour BB

Pipeline de traitement d'un paquet reçu
1. Déduplication ID = senderID_hex + timestamp_ms + messageType Bloom filter · 10 000 entrées · faux positifs 0.01% · expiration 5 min
2. Validation timestamp Rejet si écart > ±120 secondes Anti-replay sans état centralisé
3. Destinataire ? Paquet pour moi → remonter à l'application Paquet pour autre → décision relay
4. Décision relay TTL = 0 → DROP · Nœud dense → relay probabiliste 50-70% Ingress suppression : ne pas renvoyer vers la source
5. K-of-N Fanout déterministe Hash(messageID) → sous-ensemble fixe de voisins Load balancing · pas de coordination · même message = même subset
6. Transmission Write without response vers chaque voisin sélectionné Fragments staggered pour éviter la saturation

Store-and-Forward
Cache local avec TTL
  • Messages pour peers offline : queue locale TTL 24h
  • Favoris : stockage potentiellement indéfini
  • Livraison automatique à la reconnexion
  • Nettoyage des messages expirés en background
  • Pas de synchronisation de graphe (contrairement à Briar)
Fragmentation — Calcul précis
overhead = 13 (header) + 8 (senderID) + 8 (recipientID) + 13 (fragment metadata) = 42 bytes
chunk_size = max(64, MTU - 42)
Avec MTU 512 bytes → chunk_size = 470 bytes ≈ 469 bytes par défaut
Message 1200 bytes → 3 fragments BLE
Leçons directement applicables à BB
  • Pipeline déduplication : adopter le même ordre (Bloom → timestamp → relay)
  • ID dédup format : senderID + timestamp + type → compact et efficace
  • Ingress suppression : ne jamais renvoyer vers la source d'un paquet
  • Jitter avant relay : 20-200ms pour éviter les collisions radio
  • TTL adaptatif : relay probabiliste si degré de connexion élevé
  • Write without response : plus rapide que write with response
Synthèse BitChat → BB
BitChat a résolu empiriquement des problèmes que BB doit résoudre formellement. Leur code n'est pas réutilisable (Swift/GATT) mais leur architecture est notre meilleure référence. Le CDS/MPR de BB donne des garanties topologiques que le K-of-N probabiliste de BitChat n'a pas.

04 — FORWARDING

CDS Greedy vs MPR — Réduction des transmissions BLE

GATT Phase 1 (write without response) · L2CAP CoC Phase 2 (parallèle natif)

Flooding naïf (10 nœuds) 45 transmissions BLE — référence 100%
CDS Greedy (Phase 1) 18 transmissions BLE — réduction de 60%

Relation CDS / MPR — MPR = algorithme · CDS = résultat
CDS — Connected Dominating Set
  • Sous-ensemble de nœuds formant un backbone connexe
  • Règle : nœud X rejoint le CDS si 2 de ses voisins ne sont pas voisins entre eux
  • Seuls les nœuds CDS retransmettent → couverture garantie
  • Info requise : voisinage à 2 sauts uniquement (via messages Hello)
  • Résultat : N transmissions → backbone minimal
  • CDS Greedy : construction greedy retenue en Phase 1
MPR — Multipoint Relays
  • Méthode d'élection du CDS inspirée d'OLSR
  • Chaque nœud choisit le sous-ensemble minimal de voisins qui couvre tous ses voisins à 2 sauts
  • MPR = algorithme | CDS = résultat

Gestion des clés de groupe — 3 options
Option A — Clé statique partagée
  • Simple, overhead zéro
  • 1 membre compromis = groupe entier compromis
  • Pas de forward secrecy · Révocation impossible
Option B — Session key par paquet (Phase 1)
  • Forward secrecy parfaite
  • Révocation : exclure du key header
  • Overhead : N × 32 bytes (≤ 15 membres OK)
  • 5 membres = 160 B · 10 membres = 320 B · 20 membres = 640 B
  • Key rotation périodique → anti-replay multihop
Option C — ECDH éphémère (Phase 2)
  • Overhead constant — indépendant de N
  • Forward + backward secrecy
  • Latence ECDH au join/leave ~50 ms
  • Contribution originale mesurable
