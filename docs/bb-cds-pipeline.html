02 — Objectif CDS

Pourquoi un CDS ?

Un Connected Dominating Set = sous-ensemble de nœuds RELAY qui dominent le graphe et restent connectés entre eux. Les autres sont LEAF.

Sans CDS (full mesh)

  • Chaque nœud dial tous les autres
  • Explosion de liens BLE (churn, timeouts)
  • Forward partout = flood coûteux

Avec CDS (backbone)

  • Relais interconnectés
  • Feuilles se rattachent à un dominateur
  • Forward ciblé sur le backbone
Réf. algo : Wu & Li 1999 · formulation paper arXiv:2509.00967 §2.4.2 · code src/forwarding/cds.py (am_i_cds).

04 — Presence OTA

Hello sans connexion

Chaque nœud diffuse un Hello public dans le Manufacturer Data d’une publicité legacy connectable (pas Extended AD — invisible sur beaucoup de contrôleurs Pi).

Format presence v0x02 (compact)

  • Magic BB + proto 0x01 + format 0x02
  • anon_id 8 B · seq · flags (bit0 = RELAY)
  • BD_ADDR L2CAP joignable (6 B)
  • Listes voisins/MPR : vides (budget ~27 B)

Conséquence design

  • Tout scanner legacy entend la présence
  • Élection CDS « air » faible (pas de listes)
  • Compensé par politique dial every heard
  • Flag RELAY toujours utile dès qu’un nœud s’élit
Extended Advertising (D-Bus) a été retiré du chemin prod : les boards qui ne scannent qu’en legacy ne voyaient personne.

06 — Élection Wu-Li

RELAY ou LEAF ?

am_i_cds(local, table, peers) — décision locale, pas de coordinateur.

Conditions pour être RELAY

  • ≥ 2 pairs symétriques
  • Au moins une paire de pairs non adjacents entre eux (gateway)
  • Non élagué par la règle d’id §2.4.2 (Cases 1/2)

Cas typiques

  • Étoile hub = RELAY, feuilles = LEAF
  • Clique radio tout le monde adjacent → CDS vide → tous LEAF
  • Ligne A—M—B M = RELAY (seul pont)
Sur le tip legacy, listes voisins OTA vides → symétrie Hello souvent pauvre → CDS air souvent vide. Ce n’est pas un bug : la suite du pipeline compense.
07 — Politique de dial

Qui ouvre quel lien ?

BBNode._backbone_dial_targets() — directionnalité explicite, pas de tie-break BD.

SituationQui dialCible
Je suis RELAY + voisins relaysRELAYautres relays d’anon_id plus grand (un seul sens)
Des relays existent, je suis LEAFLEAFdominateur = relay d’anon_id minimal
Aucun relay CDS (CDS vide)Chacuntous les peers heard avec BD_ADDR connu

Pourquoi pas un hub fixe ?

« Heard » (AD) porte plus loin qu’un lien L2CAP durable. Un hub hors de portée isole des feuilles. Le full-heard laisse chaque nœud lier ce qu’il peut vraiment atteindre.

Garde-fous RF

  • 1 dial / passe de connect
  • Timeout dial 8 s (non-bloquant)
  • force=True (bypass tie-break BD)
  • Backoff ETIMEDOUT → arrête de saturer

Deux régimes

09 — Forward

Qui relaie les paquets ?

PacketForwarder._should_relay() — deuxième filet après l’élection OTA.

Règle

Forward si :

  • CDS RELAY hello_mgr.is_relay, ou
  • ≥ 2 liens L2CAP actifs (pont dans le graphe réel)

Anti-boucle : cache « seen » + TTL.

Pourquoi ≥ 2 liens ?

AD = graphe complet → CDS vide. L2CAP = étoile (portée réelle). Le centre n’est pas RELAY OTA mais doit bridger ses feuilles, sinon le multihop est cassé.

Forward opaque : un relais d’un autre groupe ne déchiffre pas ; il transporte quand même (bulles privées / mesh ouvert).

11 — Story de démo

Script de présentation (5 min)

  1. Contexte — mesh BLE multi-hop, pas de liste d’adresses.
  2. Presence — montrer un log « candidat découvert » sans --topology.
  3. Rôle — ligne d’état RELAY · N peer(s) / LEAF.
  4. Dial — expliquer backbone vs dial-heard (slide 8).
  5. Chat — message A→B via M ; sur M : non déchiffrable si autre clé.
  6. Filet — « même si CDS air vide, ≥2 liens font forward ».
Commande démo : sudo python3.14 bb_node.py --chat · même GROUP_KEY + TRANSPORT=ble_l2cap partout.
